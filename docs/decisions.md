# Decisions log

Ambiguities resolved during the build (spec section 0, rule 9). Each entry picks the
simplest option consistent with the frozen PPT contract (spec section 1.2). Newest phase last.

## Phase 1: Foundation

| # | Topic | Decision | Why |
|---|---|---|---|
| D1 | Repo root | The spec's `apaar-ledger/` root **is** this repository's root (`/`), not a subfolder. | Avoids a pointless extra level; layout below the root matches spec section 3. |
| D2 | API prefix and health | All endpoints live under `/api/v1` (spec 8). `/health` is served at **both** `/health` and `/api/v1/health`; OpenAPI UI stays at FastAPI's default `/docs`. | Container health checks and the spec's "/docs loads" criterion both use un-prefixed paths. |
| D3 | Login request format | `POST /api/v1/auth/login` uses the standard OAuth2 password form (`application/x-www-form-urlencoded`, `username` = email). `POST /auth/refresh` takes JSON `{refresh_token}`. | Spec 3 says "OAuth2 password flow"; this also makes Swagger's *Authorize* button work. |
| D4 | JWT library | PyJWT (HS256) instead of python-jose. | The spec names JWT, not a library; PyJWT is smaller and actively maintained. |
| D5 | Source of truth for roles | Tokens carry `role`, `inst`, `apaar` claims for the UI, but the server re-loads the user on every request and authorises on the **DB role and `active` flag**. | A changed or deactivated account takes effect immediately; a forged role claim gains nothing (tested). |
| D6 | Refresh tokens | Stateless refresh tokens (7 days), a new pair on each refresh; no server-side revocation list in Phase 1. | Simplest working option. Deactivating a user (`active=false`) blocks both access and refresh. |
| D7 | Other institutions' rows | Institution users requesting another institution's resource get **404**, not 403. | Does not disclose that the other institution's record exists (same spirit as FR-9 / FR-37). |
| D8 | Institution scoping helper | `app/core/rbac.py::scope_to_institution()` is the single shared helper. It **fails closed**: VERIFIER and STUDENT see no institution-owned rows through it (they get dedicated consent-gated endpoints in Phase 7). | Spec 4 / 12: "row-level scoping in every query via one shared helper". |
| D9 | Enum storage | Roles, programme levels and shifts are stored as `VARCHAR + CHECK` (SQLAlchemy `native_enum=False`), not native Postgres enums. | Adding values later is a simple migration. |
| D10 | `users.full_name` | Added a nullable `full_name` column to `users` (not in spec 7.1). | Needed for the shell header; harmless. |
| D11 | Placeholder APAAR ID | The demo student is linked to `990274831650`. The `99` prefix marks it as synthetic (spec 10); the number avoids the "all same digit" and "sequential run" patterns that FR-6 flags. **Phase 2's MOCK registry must contain this ID.** | The APAAR registry is Phase 2; Phase 1 only needs a placeholder link. |
| D12 | Seed data | The Phase 1 seed (`app/db/seed.py`) is idempotent and runs on every API start: 3 demo institutions, 8 programmes, 9 institution-programme rows for academic year `2025-26`, and one account per role. All demo accounts share the password `Demo@2026` (env `DEMO_PASSWORD`). Institution and programme names/codes are **synthetic** (prefixed "Demo"/`DEMO-`), not real institutions or real AICTE codes. | One-command demo; does not impersonate real organisations. The national 40-institution dataset is Phase 2 (`POST /demo/seed`). |
| D13 | Maker and checker institution | The demo maker and checker both belong to `DEMO-INST-001`. | Maker-checker (Phase 4) needs both roles in the same institution. |
| D14 | Test database | pytest runs against **real PostgreSQL** (`TEST_DATABASE_URL`, must end in `_test`). It drops and rebuilds the schema through Alembic, then seeds. Compose creates `apaar_test` on first start (`backend/db-init/`). | Later phases depend on PG-only features (`FOR UPDATE`, `pg_trgm`); SQLite tests would give false confidence. Running Alembic in tests also checks the migration. |
| D15 | Web container | The `web` service runs the Vite dev server and proxies `/api` and `/health` to `api:8000`. The browser therefore talks to one origin; CORS is still restricted to `CORS_ORIGINS`. | Fewest moving parts for a local demo (no nginx config). |
| D16 | Token storage in the browser | Access and refresh tokens are kept in `localStorage`. | Simplest for a prototype; production would use httpOnly cookies. Listed as a known limitation. |
| D17 | Deferred within Phase 1 scope | The hash-chained audit log (FR-35) arrives in Phase 4 and login rate limiting in Phase 9 (both as the spec schedules them). Phase 1 writes **no audit entries**, including for logins. | Follows the build order in spec 15. |
| D18 | bcrypt pin | `bcrypt==4.0.1` alongside `passlib[bcrypt]==1.7.4`. | passlib 1.7.4's backend self-test breaks with bcrypt >= 4.1. |

Phase 1 demo rows were extended (DEMO-INST-002 PGDM-FIN; DEMO-INST-003 DIP-CE second shift and DIP-ME) so that every institution has 3-8 programmes; the programme catalogue grew to 22 synthetic codes. | Keeps demo logins meaningful and the demo institutions predictable. |

## Phase 3: Rule engine, Seat Ledger, timeline/transfer logic, Student Record Form

| # | Topic | Decision | Why |
|---|---|---|---|
| D37 | Rule codes for FR-12 | The spec names no codes for FR-12, so they are: `FN_NATIONALITY_INVALID` (ERROR), `FN_ID_DOCUMENT_MISSING` (WARNING), `OCI_NUMBER_MISSING` (ERROR), `NRI_SPONSOR_MISSING` (ERROR), `ADMISSION_OUTSIDE_WINDOW` (WARNING), `DOB_IMPLAUSIBLE` (WARNING), `REQUIRED_FIELD_MISSING` / `FIELD_INVALID` / `PROGRAMME_NOT_APPROVED` (ERROR). Unspecified severities: `APAAR_NOT_FOUND` ERROR, `TIMELINE_INVALID_DATE` ERROR, the other timeline codes WARNING. A missing APAAR ID is `APAAR_INVALID` with `evidence.reason = "missing"`. The full table lives in `rule_engine.RULE_CODES` and the README. | ERROR = data that cannot be right; WARNING = may be legitimate and needs a justification (spec 5.2). A late admission or a pre-APAAR diploma can be genuine. |
| D38 | Duplicate vs overlap | For another enrolment of the same APAAR ID that overlaps in time (after the transfer rule): same institution + programme + academic year -> `DUP_EXACT_SAME_INST` (ERROR); same institution, other programme, both full-time -> institution-visible `TIMELINE_OVERLAP` WARNING (own data, no case); other institution, **same academic year** -> `DUP_EXACT_CROSS` case; other institution, different year, both full-time -> `TIMELINE` case (code `TIMELINE_OVERLAP`). Both cross-institution cases are `AICTE_ONLY`; the institution gets only `ENROLMENT_ELSEWHERE_NEUTRAL`. | FR-9 and 9.5 describe overlapping concepts; this split gives one finding per situation. |
| D39 | Pair direction | Pairwise checks compare a record only with enrolments submitted before it (every stored one for a new record; lower record ids when re-validating stored data). A pair is reported once, on the later submission. The lateral-entry prior check looks at all enrolments. | Matches what happens at submission time and keeps the replay consistent with the live path. |
| D40 | Transfer semantics | Spec 9.1 rule applied first: if the other enrolment's `end_date <= admission_date` it is not a duplicate. It is a transfer (INFO `TRANSFER_DETECTED`, no case) only when the earlier enrolment was left without completing (status not `GRADUATED`); a completed one is a prior qualification (used by the lateral check, no message). The INFO text is neutral (no institution or dates). | A completed diploma before lateral entry is progression, not a transfer; flagging it would be noise. |
| D41 | Privacy of cross-institution checks | Exact matching keys on the person row (`students.apaar_id` is UNIQUE, so the same APAAR ID is the same `students.id`). Institution-facing outcomes are built from a boolean only ("possible enrolment elsewhere" / "history needs verification"); their `evidence` is empty. Case dedupe keys and case evidence use `privacy_tokens.apaar_token()` (HMAC of the APAAR ID), never the raw ID. Full details (other institution, dates) exist only in `AICTE_ONLY` case evidence. Added neutral code `TIMELINE_CHECK_NEUTRAL` for cross-institution timeline cases that are not "active enrolment elsewhere". | FR-9, FR-37. Matching on plaintext happens inside the AICTE trust boundary, as the README's honest-limit note says. |
| D42 | Timeline model | Interval = admission to `end_date`, or a projected end of admission + programme duration (one year less for lateral entry) when no end date is reported. `TIMELINE_TOO_SHORT`: a `GRADUATED` enrolment ending before admission + duration - tolerance (rule `timeline.min_duration_tolerance_months`, default 6). It fires on the graduated record itself; a lateral entrant whose only completed priors are too short gets an AICTE-only `TIMELINE` case if the prior is elsewhere. `TIMELINE_INVALID_DATE`: admission after today (server date) or end before admission. | Academic years end in May-June, so a strict "N full years" check would flag every genuine graduate. |
| D43 | FN passport/ID note | FR-12 requires a passport/ID note for foreign nationals, but spec 7.1/7.2 have no such field. Migration `0003` adds `student_records.id_document_note_enc` (Fernet) and the API accepts an optional `id_document_note`; the generator writes a deterministic synthetic note for FN records (derived from the record key, no RNG draw, so the dataset is otherwise unchanged). | Needed to implement FR-12 as written without flagging every seeded FN record. |
| D44 | Engine thresholds as rules | New `quota_rules` keys (versioned, CONFIGURABLE): `timeline.min_duration_tolerance_months` (6), `validation.age_at_admission` (UG 16-35, DIPLOMA 14-35, PG/PGDM/MCA 19-60, OTHER 14-60), `validation.apaar_suspicious` (run length 6; ascending or descending, no wrap-around), `validation.name_match` (85). Name score: 100 for the same normalised tokens in any order, 95 initials-compatible, 92 same Double Metaphone keys, 90 when a 2+ token name is contained in the other (missing middle name), else RapidFuzz `token_sort_ratio`. `rapidfuzz` added to requirements. | Rules-as-data (P21) covers validation thresholds too. On the seeded data the check flags exactly the 5 injected DOB mismatches and none of the 400 registry spelling/script variants. |
| D45 | Single-record creation now | `POST /students` (maker, own institution) is implemented in Phase 3 so the Student Record Form can save: ERRORs -> 422 `RECORD_HAS_ERRORS` with the outcome list (nothing stored); otherwise the record is stored `PENDING_APPROVAL` with `batch_id = NULL`, takes its seat (flag mode), and rises T0 -> T1 (`trust_events`, actor `system:rule_engine`). Over-cap never blocks. Checker approval of these records, updates/versioning beyond v1 and uploads stay in Phase 4. | The form needs a save path, and FR-10 / the flag-not-reject test need a real admission path. |
| D46 | Existing APAAR on create | If the APAAR ID already has a `students` row, the new record reuses it (the row keeps the first-submitted name/DOB, D21); this submission's name and DOB are kept in the version snapshot (name Fernet-encrypted). | Keeps APAAR as the person key without overwriting what another institution submitted. |
| D47 | Flag invariant | In each bucket the seat holders are ordered by when they took their seat; the first `cap` are clean and the rest have `over_cap = true`, so flagged records always equal `excess = max(0, used - cap)`. `admit()` assigns the flag at admission; `release()` and cap changes re-derive the flags under the bucket lock (releasing a clean seat moves the earliest flagged record within the cap). | Keeps "over-cap flags (count and excess)" consistent on dashboards and makes "releasing 3 lowers excess by 3" hold whichever records are released. |
| D48 | Over-cap cases | One `OPEN` `SEAT_OVER_CAP` case per (institution-programme, bucket), keyed `SEAT_OVER_CAP:{ip}:{bucket}` in `subject_ids_json.key`; a partial unique index (`uq_cases_open_key`) allows only one OPEN case per key. The case is `AICTE_ONLY` but carries `institution_id` for filtering. It is closed automatically (RESOLVED) when `used <= cap`. After "Accept exception" (RESOLVED), a later over-cap admission opens a new case. Lock order is always balance row, then case; the decision endpoint takes the bucket lock before re-reading the case. | Atomic under concurrency; no deadlock between decisions and admissions. |
| D49 | Caps and rule changes | The balance row stores `cap`. `admit()` recomputes the bucket's cap from the active rules under the lock; `PUT /rules/{key}` for a `bucket.*` key recomputes every balance immediately (flags and cases re-derived). A version with a future `effective_from` takes effect at the next admission into a bucket (or the next PUT). Active version = highest `version` with `effective_from <= now()`; keys with no row use the code defaults. | Spec 7.3: "changing a rule recomputes cap values; no code change". |
| D50 | Rules endpoints | `GET /rules` and `PUT /rules/{key}` are `AICTE_ADMIN` only (as instructed for this phase; spec 8 marks them "admin"). PUT appends a version (never edits), validates the value's shape per key, rejects unknown keys (404), and records `updated_by`. The audit entry for rule changes arrives with the audit log (Phase 4). | Rules-as-data with a version history (spec 11 item 13 editor UI is Phase 4+). |
| D51 | Replay of seeded data | `seed_national()` ends with `synth/replay.py`: all records are validated (bulk-prefetched context) and seated per bucket in admission-date order with `seat_ledger.admit_many()`, which runs the `admit()` algorithm for several records under one lock (equivalent to sequential `admit()` calls in one transaction). Seeded records keep their historical status (ACTIVE even when over cap, rather than `PENDING_APPROVAL`); records with an ERROR stay T0 but still hold their seat (they are stored, already-admitted students); the others rise to T1 (`trust_events`, actor `system:replay`). Adds about 16-20 s to a national seed. | "Never fake results": flags, cases and tiers come from the real code paths (D25); historical admissions were not made through this system. |
| D52 | Institution APAAR lookup | No institution-scoped registry endpoint was added; `GET /mock/apaar/{id}` stays AICTE-only (D22). The form's "APAAR lookup status" comes from `POST /validate/record`'s `apaar_status`: `format_ok`, `suspicious`, `found`, `name_match`, `dob_match` booleans, never the registry name/DOB. | Institutions can confirm what they typed without reading registry contents. |
| D53 | Seat projection in dry run | `POST /validate/record` also returns a read-only `seat_projection` (bucket, cap, used, used after, excess after, would be flagged) without locking or writing; the authoritative decision is made by `admit()` at save time. | P4 "dry-run shows it" for single records; Phase 4 builds the batch version. |
| D54 | Cases API scope in Phase 3 | `GET /cases`, `GET /cases/{id}` and `POST /cases/{id}/decision` exist now; visibility is enforced by `rbac.scope_cases()` next to `scope_to_institution()`. Decisions are implemented for `SEAT_OVER_CAP` only (FR-11); other types return 400 until the Phase 5 review queue. No `RULE_WARNING` cases are opened: warnings live in `validation_results` (justification flow is Phase 4). | Smallest surface that makes FR-11 usable and testable. |
| D55 | FR-11 notifications | "Request correction" writes one `notifications` row (kind `SEAT_CORRECTION_REQUESTED`, MOCK channel) per active maker/checker of the institution, with its own record ids, bucket, programme and the officer's note; no case id (the case is AICTE-only). | Spec 2.2: notifications are a table shown in the UI. |
| D56 | Programme suggestions | Placeholder until ML-4 (Phase 5): exact code, then code/name prefix, then substring, against the institution's approved programme rows for the year, in the form (client side) and in `PROGRAMME_NOT_APPROVED.suggested_fix` (server side). | Task allows a simple match now. |
| D57 | Current academic year | New setting `CURRENT_ACADEMIC_YEAR` (default `2025-26`): records without an explicit `academic_year` are filed under it. | Keeps D12/D27's single current year configurable. |

## Phase 4: Upload pipeline, maker-checker, hash-chained audit, trust tiers T0-T2

| # | Topic | Decision | Why |
|---|---|---|---|
| D58 | Batch source | Migration `0004` adds `upload_batches.source` (`UPLOAD` / `FORM` / `CORRECTION`) plus file metadata (filename, academic year, chunk count, SHA-256, the encrypted CSV, the stored dry-run and submit results, justification, timestamps). A record saved through the Student Record Form now gets its own one-row `FORM` batch in `PENDING_APPROVAL` (this replaces D45's `batch_id = NULL`), so the checker approves form records and uploads through the same `/batches/{id}/approve|reject`. | One maker-checker path for every way a record enters. |
| D59 | Chunks and finalize | Chunks are stored Fernet-encrypted (they hold contact data, FR-38). Before finalize a re-sent chunk replaces the stored one (resume after a dropped connection); `GET /uploads/{id}` lists received chunks. Finalize assembles chunks `0..n-1`, checks the header against spec 7.2, and stores the encrypted CSV and its SHA-256. Finalizing again returns the stored result (`idempotent_replay: true`) and writes nothing; after finalize, chunks are frozen (an identical re-send is a no-op, a different one 409). Limits (settings): 5 MB per chunk, 50 MB per file, 2,000 chunks, 50,000 rows. | FR-2: chunked, resumable, idempotent re-finalize. |
| D60 | CSV format | The header may spell the column `dob(YYYY-MM-DD)` (as in spec 7.2) or `dob`. Optional extra columns: `id_document_note` (D43) and `academic_year`. Unknown columns are ignored and reported as a note. Booleans accept true/false/yes/no/1/0/blank. Dates must be `YYYY-MM-DD`; a `DD/MM/YYYY` value gives `FIELD_INVALID` with the ISO date as the suggested fix. Defaults: shift `REGULAR`, entry type `REGULAR`, mode `FULL_TIME`. Row numbers count data rows (row 1 is the first student), skipping blank lines. | Tolerant of how registrars fill spreadsheets, strict about what gets stored. |
| D61 | Dry run | Every row goes through the Phase 3 rule engine, and rows of the same file are checked against the rows above them (an in-memory overlay with pseudo ids, so a student listed twice is caught). The seat projection is computed in memory from the current balances, read without locks: one projected `SEAT_OVER_CAP` WARNING per over-cap row, plus a per-bucket impact panel ("Rows 1, 2, 3: would exceed APPROVED by 3 ..."). Nothing goes to `student_records` or the Seat Ledger. The dry run does store its own report (`validation_results` rows with no record, and the summary on the batch) so the report can be reloaded; it can be re-run. Codes without a rule-specific fix get a generic hint (`FIX_HINTS`). | FR-3. Storing the report is not a write "to the repository". |
| D62 | Submit | Allowed only after a dry run. The file is re-validated at submit time, because other data may have changed since the dry run. ERROR rows refuse the submission (422 `BATCH_HAS_ERRORS`) unless `exclude_error_rows` is set; excluded rows are not stored, but their findings are kept on the batch. Rows with a rule WARNING need a justification, either per row or for the whole batch (422 `JUSTIFICATION_REQUIRED`); justifications are stored with the outcomes. Whether a row goes over cap is decided under the bucket lock at submission and never blocks it (flag mode); the wizard still asks for a justification whenever the dry run shows a warning, projected over-cap included. Order: rules -> bulk insert at T0 (with version 1) -> cases -> `admit_many` per bucket in (programme row, bucket) order -> T1/T2 -> `PENDING_APPROVAL`. The batch row is locked `FOR UPDATE`, so concurrent submits serialise, and a re-submit returns the stored result (`idempotent_replay: true`) and writes nothing. Measured on the local test cluster during development, 10,000 rows took 6.2 s for the dry run, 24 s to submit and 4.6 s to reject. | FR-17 pipeline order; spec 13 idempotency; NFR-5. |
| D63 | Checker decision | Only `INST_CHECKER` of the batch's institution can decide; AICTE roles can view batches but not decide them (maker-checker is an institution control).
